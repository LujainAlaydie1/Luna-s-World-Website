LSquared · Luna’s World

Website design guide

How lunasworld.lsquared.sa should look and feel so it is clearly the same product as the iOS app. Everything here is taken from the app’s design system (the “v2” redesign) and from the live site’s CSS. Samples on this page use the real component rules, so what you see is what the site renders. Internal document: not published with the site.

01The vibe, in one paragraph

A warm, hand-drawn paper feel. Cream background, dark olive ink, flat hard-edged offset shadows (never blurred), fully rounded pill buttons, friendly Baloo headings, and a cat-lover’s tone. Arabic comes first and everything works right-to-left. It should feel like a sticker-book, not a SaaS landing page.

Ink-outlined everything

Cards, buttons and pills all have a 1.5px (2px for big blocks) border in the ink colour. This is what makes it feel hand-drawn.

Flat offset shadows

3px right, 3px down, zero blur. On hover the element “presses” 1px toward the shadow. No soft drop shadows anywhere.

Round and friendly

Pills are 100px radius. Cards are 14–26px. Nothing has sharp corners.

Arabic first

Default markup is Arabic and RTL; English is a toggle, not a translation tacked on. Every string exists in both.

Calm and honest

No ads, no trackers, no pop-ups, no dark patterns. The site loads no outside fonts or scripts, and says so.

Colour rules

Do

  • Text is ink or ink-soft. Headings are forest-deep.
  • Links and primary actions are forest.
  • Use gold and rose as fills, dots, numerals and small accents.
  • One strong accent per block. Cream and white do most of the work.

Don’t

  • Don’t put gold text on cream (1.8:1). Don’t use pure black or pure white backgrounds in light mode.
  • Don’t use gradients, glows, glassmorphism or blurred shadows.
  • Don’t introduce new brand colours. Add a variable and a dark value first.

06Arabic and English together

  • Markup pattern: every visible string is a pair, <span class="en">…</span><span class="ar">…</span>. CSS hides the inactive one using html[lang]. Arabic is the default on first load; the choice is remembered in localStorage.
  • Direction: html[dir] flips with the language. Use logical properties (padding-inline-start, inset-inline-end, text-align: start, margin-inline) so layouts mirror for free. Avoid left/right.
  • Mirror: arrows, chevrons, “next” icons and progress bars flip in RTL. Logos, photos, phone numbers, emails and code do not.
  • Mixed text: wrap Latin names (LSquared, Firebase), emails and URLs inside Arabic sentences normally. If punctuation lands on the wrong side, wrap the Latin run in <bdi>.
  • Arabic copy rules: write to the user in the masculine/neutral form by default (matches the app). Use “تطبيق” and “حساب” rather than English loan-words where a natural Arabic term exists. Keep the same meaning as the English; don’t translate word-for-word.
  • Length: Arabic is usually shorter than English; design for the longer one in each slot so the toggle doesn’t make the layout jump.
  • Legal pages: the Arabic text controls if the two versions differ (stated in the Terms).

07Dark mode

Controlled by html[data-theme="dark"], set by the ☀️/🌙 toggle and remembered as lunasworld-theme (default light). It swaps the variables above: near-black #101010 background, #191916 cards, light ink #D6D3C6, and brighter greens. Borders stay ink-coloured (now light) so the outlined look is preserved; shadows become a softer black. Use the toggle at the top of this page to preview.

  • Never hard-code a colour in a component; use variables so it flips with the theme.
  • Images with white backgrounds need a dark variant. The logo and app icon already have .logo-light/.logo-dark and .appicon-light/.appicon-dark pairs; follow that pattern for new art.
  • The OS preference (prefers-color-scheme) is not read at the moment: the site starts light and remembers the visitor’s choice. Consider defaulting to the OS setting for first-time visitors.

Checklist for every page

  • Real headings in order (one h1, then h2, h3). Landmarks: nav, main/sections, footer. Language set on html and updated by the toggle.
  • Everything reachable and operable by keyboard; visible focus ring (never outline: none). Toggle buttons use aria-label/aria-pressed.
  • Tap targets at least 44×44px on phones. No horizontal scroll at 375px. Body text never below 14.5px.
  • Emoji used as decoration, not as the only meaning. Images have alt; decorative ones use empty alt.
  • Respect reduced motion: only 0.12–0.2s transitions are used, and nothing auto-plays.

09Voice and content

Sounds like

  • A friendly neighbour who loves cats: warm, short sentences, plain words.
  • “You” and “we”. Concrete: say where the button is (“Menu → Settings → Delete account”).
  • Honest limits: “It’s a fun estimate, not a diagnosis.”
  • Gentle emoji (🐾 🐱) as seasoning, one per heading at most.

Never

  • Hype (“revolutionary”, “AI-powered”), pressure, or fake urgency.
  • Medical promises. Health content is information, never diagnosis.
  • Claims we can’t back up: “no ads”, “no GPS”, “private health records” are true today; re-check before repeating them.

What not to advertise yet

Until they launch publicly, do not mention: vet consultations / video calls and payments, the clinic directory and bookings, volunteer events, the health passport, or group-invitation links. They exist in the code but are switched off. Mention them only when the app version that turns them on is live, and update the Privacy Policy and Terms at the same time.

Imagery

  • Use the app’s own illustrated cats, the logo mark and the real app screenshots (light and dark pairs). Phone screenshots sit inside a plain rounded frame, no fake device chrome.
  • App icon on the hero: 120px, 28px radius, 2px ink border, 5px offset shadow.
  • Social share image is og-image.png, 1200×630, cream background with the logo. Regenerate when the tagline changes.
  • Stock photography of real cats is welcome if it is warm and natural. Avoid glossy 3D renders and clip-art paws.

10Adding or changing a page

  1. Duplicate privacy.html (simple page) or index.html (marketing page). Keep the head, nav, footer and bottom script exactly as is.
  2. Change the <title> (Arabic · English, two to four words each), description, canonical, og:url, and the JSON-LD block if the page needs one.
  3. Write every string in both languages, using the span pair. Use only the variables and components on this page.
  4. Add the page to sitemap.xml and the footer links. Pages use clean URLs on Vercel (/privacy), and internal links keep the .html form.
  5. Test at 375px and desktop, in Arabic and English, in light and dark. Run through the checklist in section 08.
  6. Update the “Last updated” date on any legal page whenever its text changes.

Site constraints

  • Static HTML only, hosted on Vercel; no build step, no framework, no CDN, no cookies, no analytics. If any of that changes, update Privacy Policy section 14.
  • Each page is self-contained (fonts and CSS inlined), so it stays around 300–500 KB. Keep new images optimised (WebP/PNG under 200 KB).
  • The docs/ folder is for internal reference and is excluded from the deploy by .vercelignore.

11Quick don’ts

  • No blurred shadows or gradients
  • No new fonts or icon libraries
  • No left/right CSS in RTL-sensitive spots
  • No tracking pixels, chat widgets or cookie banners
  • No English-only or Arabic-only pages
  • No pure black/white page backgrounds
  • No more than one primary button per section
  • No text under 14px
  • No mention of switched-off features
